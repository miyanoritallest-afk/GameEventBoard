## 2. 固定ルーティン（1画面 = 1PR）

各画面はこの順で進める。ユーザーとの分担が決まっている。

1. **現状把握（自分）** — 対象 `page.tsx`（＋使っている board/form 等 client component）を読み、情報設計・データ構造・既存挙動（プライバシー・空表示・形式分岐など維持すべきもの）を把握。
2. **情報設計の壁打ち（自分↔ユーザー）** — 論点を「案 → メリット/デメリット → 推奨」の形で `AskUserQuestion` で提示。ユーザーの好みは**判断根拠とデメリットを必ず出す**こと。図（ASCII）で見せると通じやすい（レイアウトの選択肢など）。
3. **Claude Design 用プロンプト案を作る（自分）** — 壁打ち結論を全部盛り込む。scratchpad に保存しつつ全文をチャットに出す。リポジトリ直読み前提・`.theme-matchpoint` 踏襲・参照すべき既存実装（`docs/design-refs/*.html` と近い画面）を明記。
4. **Claude Design で案を作る（ユーザー）** — ユーザーがプロンプトを投げ、standalone HTML を持ってくる。
5. **案HTMLを軽量版で保管（自分）** — 8〜9MB の standalone を 50KB 程度に変換して `docs/design-refs/<画面>.html` に置く（手順は §4）。
6. **実装（自分）** — 案に忠実に。**ロジック改造・新規作成が要る箇所は必ず相談**（勝手にスコープを広げない）。判定・保存・集計ロジックは原則触らず、UI とデータ整形のみ。
7. **担保（自分）** — `npm run check`（lint→typecheck→test）＋ `npm run build`。
8. **Playwright 実機確認（自分）** — 観戦者/主催者視点で実際に描画を見る（手順は §5）。
9. **`/code-review high`（自分）** — 指摘を検証して修正。既存バグを踏襲していないかも見る。
10. **devlog・メモリ更新 → コミット → PR（自分）**。
11. **ユーザーがマージ** → 次の画面へ。

## 3. 実装で守ること（重要）

### デザイン作法（刷新済み画面と統一する）
- ルート要素は `className="theme-matchpoint min-h-screen bg-background text-foreground"`（`.dark` は使わない）。
- 色は `--mp-*` 変数。**インライン style 専用で使う `--mp-*` は Tailwind v4 に tree-shake される**ので注意（§6）。
- Tailwind の任意値は `border-[color:var(--mp-border-strong)]` の形。**`border-border-strong` のような素のクラス名は無効で色が付かない**（過去にハマった）。
- 共通の作法: パンくず＋ヒーロー（kicker＋タイトル＋チップ＋導線）＋セクション。チップ・カード・影(`--mp-e1〜e3`)・角丸は刷新済み画面と揃える。
- 純粋関数（色割当・ラベル等）は `src/app/events/[id]/_components/` に共通化済み: `team-colors.ts`（`teamColor`）/ `round-label.ts`（`roundLabel`）/ `score-stepper.tsx`（`ScoreStepper`）。フォーム系でも再利用できるものは切り出す。

### セキュリティ・設計（実装ガイドラインの要点・`docs/実装ガイドライン.md` が正）
- SQLi: Supabase クエリビルダのみ。生SQL禁止。
- 認証バイパス: 操作系 Server Action は冒頭でログイン確認。
- マスアサインメント: Zod で許可カラムのみ受理。`organizer_id`/`status` 等はサーバー固定。
- 入力検証は Zod スキーマ（`app/<機能>/schema.ts`）。フォーム刷新では**スキーマは触らず UI だけ**が基本。
- 認可: 閲覧系は公開・操作系は保護（A リダイレクト＋B Server Action で弾く）。
- 日時: JST入力→UTC保存(`timestamptz`)→JST表示。
- **フォーム画面は入力検証・送信ロジックが絡む**ので、観戦ビュー等の閲覧画面より慎重に。UI 刷新でバリデーションやサーバーアクションの契約を壊さないこと。

- コードを書く前に `node_modules/next/dist/docs/` の該当ガイドを確認（AGENTS.md）。

## 4. 案HTML → 軽量版の変換手順（§2-5）

standalone HTML（8〜9MB）は `<script type="__bundler/template">` に JSON エスケープされた実HTMLが入っている。これを取り出して軽量版にする。過去 PR#97/99 で使った Node ワンライナー:

```js
// 1. template を JSON パースして実HTMLを取り出す
const fs=require("fs");
const html=fs.readFileSync(SRC,"utf8");
const m=/<script type="__bundler\/template"[^>]*>([\s\S]*?)<\/script>/.exec(html);
let out=JSON.parse(m[1].trim());
// 2. @font-face（外部フォントハッシュ）を除去、外部 script(CDN) を除去
const rootIdx=out.indexOf("  :root {"); const styleOpen=out.indexOf("<style>");
out = out.slice(0,styleOpen+7) + "\n/* [軽量版] @font-face 除去 */\n" + out.slice(rootIdx);
out = out.replace(/<script src="[0-9a-f-]{36}"[^>]*><\/script>\n?/g,"");
fs.writeFileSync("docs/design-refs/<画面>.html", out);
```

- 保管先は `docs/design-refs/`。README（`docs/design-refs/README.md`）に運用説明あり。
- 目的: 案からの乖離を防ぐ「正」をリポジトリに残す。CSS変数・レイアウト・JSX が読める形で。

## 5. Playwright 実機確認の手順（§2-8）

- 開発サーバーは動いていることが多い（`curl -s localhost:3000/events -o /dev/null -w "%{http_code}"` で確認）。無ければ `npm run dev`。
- **ブラウザプロファイルは1つ**。別セッション/手動起動のブラウザが掴んでいるとロックされ「Browser is already in use」で弾かれる。その場合はユーザーに閉じてもらう（chrome プロセスの kill は勝手にやらない）。
- **ログイン**: 「のり」で OAuth 済みのセッションが生きていることが多い（実機確認できる）。
- **URL の注意**: `/events/[id]/...` の `[id]` は **UUID を渡す**。slug（`event-xxxx`）を tournament 等に直打ちすると `22P02`（UUID変換失敗）で 500 になる。イベント詳細ページのリンク（UUID付き）を辿るか、REST で UUID を引く。
  - watch は slug/id 両対応（`isValidEventSlug` 分岐あり）。
- **実データ探索**: DBは `SUPABASE_SERVICE_ROLE_KEY` で REST 直叩きして探せる（`.env.local` にある）。例: トーナメント生成済みイベントは `のり検証1`（UUID `fc8a8b72-dbd1-43bf-b860-fed82df94b5c`、8チームフルブラケット）。
- **書き込み系を試したら原状復帰**: 結果入力等を試したら「結果を取り消し」で戻し、DB をクリーンに保つ。スクショ・スナップショット（`.playwright-mcp/`・ルート直下の png）も掃除する。
- **未確認の残課題**: 観戦ビューの「予選順位・試合結果」セクションは、DBに予選結果ありイベントが無く実機未確認。予選結果を入れたイベントで一度見ておくと万全。

## 6. 過去にハマった落とし穴（同じ轍を踏まない）

- **MP トークンの tree-shake**: インライン style 専用の `--mp-*`（例 `--mp-silver`/`--mp-bronze`/`--mp-gold`/ロール色）は Tailwind v4 に削られて無色になる。対策として `globals.css` の `@layer` 外の素ルール `.theme-matchpoint { ... }` に**再宣言**する。新しい色を足すときは両方に書く。
- **無効な Tailwind クラス**: `border-border-strong` 等は色が付かない。必ず `border-[color:var(--mp-border-strong)]`。
- **モーダルのスナップショット陳腐化**: 開いたモーダルが match のスナップショットを保持し続けると、保存後・他者更新後に古い値を出す。id 保持＋描画時に最新データから引き直す or `key` に確定値を含めて再マウント（第8/9画面で対処済み）。
- **既存バグの踏襲**: 全面書き直しで既存ロジックをコピペすると、既存のバグも運んでくる（観戦ビューで順位フィルタのバグを踏襲していた例）。`/code-review` は「新規/既存」を問わず拾うので必ず回す。
- **案に100%合わせない判断**: デザイン案がロジック/スキーマ変更を要求することがある（例: POTG を選手名にする案 → 現行は取得数で順位タイブレーク。現行維持を選択）。**現行の確定設計を壊す変更は相談**。デモ専用UI（ステージ切替・LIVEチップ等）は実装しない。
- **セクション番号など「飛び」**: 形式・進行で一部セクションが非表示になる画面は、番号を表示分だけ連番にする（固定番号だと 01→05 と飛ぶ）。
