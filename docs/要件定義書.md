# GameEventBoard 要件定義書

最終更新: 2026-06-18
ステータス: ドラフト（壁打ち合意済み）

---

## 1. プロジェクト概要

### 1.1 背景・課題
FPSタイトル（主にOverwatch 2）のファンコミュニティでは、ゲーム内イベントを頻繁に開催している。
しかしゲーム自体にイベント管理・予約機能がないため、運営は以下の手作業を強いられている。

| 段階 | 現状のツール | 課題 |
|------|-------------|------|
| ① 告知 | Discord | 情報が流れて埋もれる |
| ② 応募 | Google Form | 別管理・転記が必要 |
| ③ 参加者管理 | Excel スプレッドシート | 手作業・転記ミス |
| ④ チーム振り分け | 手作業（ランク・実力考慮） | 公平性の担保・手間が大きい |
| ⑤ マッチアップ作成 | ルールブックに手書き | トーナメント/総当たり表が作りにくい |
| ⑥ 試合スケジュール管理 | なし | いつ・誰vs誰の試合か分かりにくい |
| ⑦ 配信情報 | なし | どの配信サイト/配信者か不明 |
| ⑧ 結果・順位管理 | なし | 運営の余裕がなく未対応 |

### 1.2 解決の方向性 / プロダクトの核
> **「Discordで完結していたイベント運営を、URLひとつで回せるようにする」**

- コミュニティの拠点は **Discordのまま** とし、Discordを置き換えない。
- 面倒な部分（フォーム・Excel・手作業の振り分け・スケジュール管理）だけをアプリに移す。
- Discordには **通知だけ** を自動で飛ばす役割分担とする。

### 1.3 ターゲットユーザー
- **運営（主催者）**: イベント作成・参加者管理・チーム振り分け・進行管理。負担軽減が目的。
- **参加者**: イベント検索・応募・自分の試合/スケジュール確認・結果閲覧。
- → 運営と参加者の体験を **均等に重視** する。

## 2. スコープ（Phase 計画）

初期ゴールは「イベント運営フル（①〜⑧）」。一度に作らず段階的に進める。

### Phase 1（コア：これが回れば実戦投入できる）
| # | 機能 | 内容 |
|---|------|------|
| ① | イベント作成・告知 | 主催者がイベントページを作成、公開URL発行 |
| ② | 参加応募 | 参加者がフォームから応募（ランク・ロール等を入力） |
| ③ | 参加者管理 | 主催者が応募一覧を確認・承認/却下 |
| ④ | チーム振り分け | ランク・ロール考慮。**手動ドラッグ＆ドロップ＋補助表示** から開始 |

### Phase 2（盛り上げ：イベントを"魅せる"）
| # | 機能 | 内容 |
|---|------|------|
| ⑤ | マッチアップ生成 | トーナメント表・総当たり表の自動生成 |
| ⑥ | 試合スケジュール | 日時・対戦カードのカレンダー/タイムライン表示 |
| ⑦ | 配信情報 | 各試合にTwitch/YouTube配信リンクを紐付け |
| ⑧ | 結果・順位 | スコア入力 → 自動で順位表更新 |

### Phase 3 候補（プラットフォーム化・SNS機能）
ユーザーが作り込みたいと希望した機能群。Next.jsフルスタック内で実現可能と確認済み。
| # | 機能 | 内容 |
|---|------|------|
| 1 | イベント検索 | キーワード/タグ/日付による検索 |
| 2 | フォロー＆通知 | シリーズ/開催回/主催者をフォロー、新規開催・更新時に通知（SNS的）。重複通知はDB制約で排除（3.6.1） |
| 3 | カレンダー表示 | 参加イベントの日程をカレンダーで確認 |
| 4 | ユーザー登録・ログイン | Discord OAuth のみ（3.0参照） |
| 5 | カテゴリ・タグ付け | 「初心者限定」「ランクフリー」等。タグは開発者が事前定義したものから選択 |
| 6 | 同時申込の排他処理 | 定員に対する二重登録の防止（楽観的ロック＋DB制約の二段構え） |
| 7 | スクリム（練習試合）管理 | チーム単位で練習試合をカレンダー管理＋Discord通知（3.4.3） |

### 横断機能（全Phaseで効く）
- **認証**: Discord OAuth のみ（3.0参照）。メール・パスワードは扱わない。
- **Discord連携通知**: イベント公開・スケジュール確定・結果更新を自動でDiscordへ通知。

## 3. 主要機能の設計方針

### 3.0 認証・ユーザー識別（確定）
「識別（誰か）」と「認証（本人か）」を分けて設計する。

- **認証方式: Discord OAuth のみ**。メール・パスワードはアプリ内で一切扱わない。
  - OAuth = パスワードを当アプリに渡さず、Discordに本人であることを証明してもらう仕組み。
  - 採用理由: コミュニティ全員がDiscordを保有 → 登録ハードルゼロ / パスワード・メール管理不要 / Discord通知の宛先が自動で紐付く。
- **Battle Tag（ゲーム内ID）: プロフィール必須項目**。
  - Battle Tagは「識別・表示」用であり、**認証には使わない**（誰でも自由に名乗れてなりすませるため）。
  - 初回ログイン後に登録を必須化する。

| 項目 | 役割 | 取得元 |
|------|------|--------|
| Discord ID | 認証＋識別の本体 | Discord OAuthで自動取得 |
| Discord 名・アイコン | 表示用 | Discord OAuthで自動取得 |
| 通知の宛先 | Discord通知連携 | Discord IDに自動で紐付く |
| Battle Tag | ゲーム内識別・本人特定・振り分け表示 | 初回ログイン後にユーザーが登録（必須） |
| ロール別ランク | 振り分けの基礎データ | 本人申告＋運営上書き |

初回ログインフロー:
```
[Discordでログイン] → 初回のみ「Battle Tagを登録してください」画面（必須）
                          ↓ 登録
                     プロフィール完成 → イベント応募などが可能に
```

### 3.1 チーム振り分け（④）
- **Phase 1**: 手動ドラッグ＆ドロップ。チームごとの平均スコアをリアルタイム表示する補助つき。
- **自動振り分け（実装済み・本戦-4）**: ブロック分け画面で「自動でブロック分け」。主催者がブロック数 N を指定すると、承認済みの全チームをチームスコア降順に**スネークドラフト**（蛇行配置）で N ブロックへ配り、各ブロックの平均強さを均す。割り切れない端数は余りを出さず一部ブロックが1多い/少ない形で吸収。スコアなし（非 require_score）イベントは受け取り順で均等配置。**叩き台として即適用**し、その後は手動 D&D で微調整するハイブリッド。既存ブロック・割当は全削除して組み直す（破壊的操作のため確認ダイアログ必須）。対戦表生成済みのときはロックして実行不可（ブロックと対戦カードのズレ防止）。
- **ロール考慮**: OW2前提で **タンク1 / DPS2 / サポート2** の構成を考慮し、ロール別スコアでチーム分け。
- **チームスコア上限**: 各チームの「出場メンバーのfinal_score平均」に上限を設け、チーム間の実力を均等化する（例: 23.0以下）。振り分け・交代時に上限超過を警告/制限する（詳細は3.1.2）。

### 3.1.1 スコアリング仕様（OSL実運用ベース・確定）
チーム平均を出すために、ランクを数値化して「個人スコア」を算出する。

**基礎データ: ランク数値化（ランクテーブル）**
- 「ブロンズ5=1, ブロンズ4=2, …, チャンピオン1=40」のようにランク↔スコアの対応表を **DBのマスタテーブル `rank_definitions` で保持**（コード直書きせず、多タイトル対応・運用調整可能にするため）。

**基礎データ: ユーザーのランク申告（参加者本人が申告）**
- 「シーズン × ロール（タンク/DPS/サポート）」の2軸でランクを持つ。
- ロールスワップ可のイベント（OSL型）では **直近Nシーズン × 3ロール = 最大9個** のランクを参照する。
- 応募モーダルで本人が入力 → 送信時に自動で数値化。運営は上書き可能。

**高ランク到達ボーナス（減衰対策・人単位）**
- マスター/グランドマスター/チャンピオンに一度でも到達した経験がある人に加点する。
- 理由: OW2はプレイしないとランクが落ちるため、過去の高ランク経験者を低スコアで獲得されないための補正。
- **人単位**で最高到達ランクを1つ記録（master/gm/champion/none）。
- 加点の点数は **イベントごとに設定可能**（例: master+1 / gm+2 / champion+3）。

**個人スコアの算出式（イベント設定で変わる）**
| イベント設定 | 個人スコアの算出 |
|------|------|
| ロールスワップ可（OSL型） | 直近Nシーズン × 各ロールのスコア平均 ＋ 到達ボーナス |
| ロールスワップ不可 | 担当ロールのスコアのみで集計 ＋ 到達ボーナス |

**算出した個人スコアはスナップショット保存**
- 応募時点で算出した個人スコアを `registrations` に値として保存する。
- 理由: 後でシーズンが進みランクが変動しても、そのイベント時点の振り分け記録が変わらないようにするため（スプレッドシート運用の「個人スコア平均」列と同じ発想）。

**イベント側に持つスコアリング設定（`events`）**
| 設定項目 | 例 | 効果 |
|---------|-----|------|
| ロールスワップ可否 | 可 / 不可 | 個人スコアの算出方式を切替 |
| 申告シーズン数 | 3 | 応募モーダルの入力行数 |
| ボーナス点（master/gm/champion） | +1 / +2 / +3 | 到達ボーナスの加点 |
| リザーブ上限 reserve_slots | 2 | チーム最大人数 = team_size + reserve_slots |
| チームスコア上限 team_score_cap | 23.0 | 出場メンバーのfinal_score平均の上限（3.1.2） |

**応募モーダルのイメージ（OSL=ロールスワップ可）**
```
┌─ ランク申告 ─────────────────────────────────┐
│ 最新シーズン   タンク[ダイヤ2▼] DPS[プラ1▼] サポ[ゴールド3▼] │
│ 1つ前シーズン  タンク[___▼]   DPS[___▼]  サポ[___▼]      │
│ 2つ前シーズン  タンク[___▼]   DPS[___▼]  サポ[___▼]      │
├─ 高ランク到達経験（該当を1つ）──────────────────┤
│ ○ なし / ○ マスター / ○ グランドマスター / ○ チャンピオン   │
└──────────────────────────────────────────┘
   送信 → 個人スコア = 9個平均(or担当ロール) ＋ ボーナス → registrations に保存
```

**スコアの3段定義（用語固定・OSL準拠）**
| 用語 | 定義 | 保存先 |
|------|------|--------|
| ①個人スコア | シーズン×ロールのランクから算出した基礎値 | `registrations.individual_score` |
| ②個人ファイナルスコア | ① ＋ 高ランク到達ボーナス | `registrations.final_score` |
| ③チームスコア | **出場メンバーの ②final_score の平均** | 保存せず算出 |

### 3.1.2 チーム構成・チームスコア・交代シミュレーション（OSL実運用ベース・確定）
OSL運営で最も苦労した「リザーブを誰と交代すれば上限を超えないか」を、ツールが自動計算する。

**チーム構成（レギュラー＋リザーブ）**
- チーム最大人数 = `games.team_size`（レギュラー人数。OW2=5固定）＋ `events.reserve_slots`（リザーブ上限。OSL=2、なし=0）。
- リザーブは0〜N人で可変。**5人のみ・5+1・5+2 などチームごとに自由**（必ず満員にする必要はない）。
- 人数上限は `teams` ではなく `events` に持つ（イベント内の全チーム共通のルールであり、チーム個別属性ではないため）。

**チームスコア = 出場メンバーのみの平均**
- ③チームスコア = 出場中（レギュラー）メンバーの ②final_score の平均。
- **リザーブのスコアは平均に含めない**（平常時は出場者のみで判定）。
- チームスコアは固定属性ではなく「今誰が出ているか」に依存する**動的な値**。保存せず常に算出する（保存すると交代のたびに手更新が必要になり、OSLの苦労が再現するため）。
- `events.team_score_cap`（上限）と比較して超過を判定。

**交代シミュレーション（編成画面の中核機能・Phase1）**
- 「登録」と「出場」を分離する概念整理: ロスター（レギュラー＋リザーブ全員）と、実際に出る出場メンバーは別。
- **リザーブはロール無概念（確定）**: リザーブは「どのロールもできる控え」であり、担当ロールを持たない（OSL実運用）。したがって交代候補は**同ロール限定ではなく全レギュラー総当たり**で出す。`team_members.role` はリザーブも形式上保持するが（NOT NULL の便宜・割当時の第1希望等）、シミュレーションでは参照しない。
- リザーブBを出す場合、レギュラーの誰と交代すれば `team_score_cap` 以内かを**全パターン自動提示**する。
```
リザーブBを出すと…
  B ↔ A1 交代 → チームスコア 22.4 ✅ 上限内
  B ↔ A2 交代 → チームスコア 23.6 ❌ 上限超過
  B ↔ A3 交代 → チームスコア 22.8 ✅ 上限内
→「Bを出すなら A1 か A3 と交代可能」と提示
```
- 試合ごとの出場記録（誰が出たか）はPhase2の任意機能（`match_lineups`）。OSLでも毎試合計算していたわけではなく、編成・登録時に判断していたため、Phase1はまず編成画面のシミュレーションを作り込む。

### 3.2 ランク情報の扱い
- **方式**: 本人申告制 ＋ 運営による上書き（運営が「内部レート」を上書き可能）。
- **理由**: コミュニティ内は顔見知りで、運営が実力を把握しているため申告＋上書きで十分機能する。
- **外部API連携は採用しない（Phase 1）**:
  - FPSタイトルのランク取得APIは非公式・不安定・タイトル依存が実情。
  - パスワードを預かる方式は存在しない（規約違反・アカウント窃取リスク）。正規連携はOAuthだが、それでも取得できるのは本人確認まででランク数値は別途という壁がある。
  - API連携は将来「特定タイトル限定の便利機能」として拡張候補に留める。

### 3.3 OW2 のランク・ロール体系（設計に反映）
- ランク帯: ブロンズ 〜 チャンピオン ＋ ディビジョン（5〜1）。
- ロール: タンク / DPS / サポート（**ロールごとに別ランクを持つ** のがOW2の特徴）。
- チーム編成: 5v5（Role Queue: タンク1 / DPS2 / サポート2）。

### 3.4 多タイトル対応の方針
- **設計だけ多タイトル対応**にし、実装はOW2に絞る。
- `game_title` と「ランク体系」をテーブルとして外出しし、後からタイトル追加は **コード改修なしでデータ追加のみ** で済む構造にする。
- 最初からOW2/Apex/VALORANTを全部作り込むことはしない（過剰）。

### 3.4.0 応募フロー設計（多パターン共存・確定）
設計思想: **「フローも入力項目もハードコードせず、イベント設定としてデータで持つ」**。
これにより、新しいイベント形式が出てもコード改修なしで運営が設定するだけで対応できる。

**2つの設定軸でフローを表現**
- `entry_type`（参加表明の単位）: `individual`（個人） / `team`（チーム） / `mixed`（両方＝OSL型）
- `team_formation`（チームの作られ方）: `self`（自分で組む） / `organizer`（運営が振り分け） / `none`（チームを作らない＝VC集合）

| 実イベント例 | entry_type | team_formation |
|------|------|------|
| OSL（ハイブリッド） | mixed | 個人=organizer / チーム=self |
| 単発：VC集合だけ | individual | none |
| 単発：運営がチーム決め | individual | organizer |
| ガチ：チーム応募のみ | team | self |

**OSLハイブリッドの表現**: `events.entry_type='mixed'` とし、各応募が `registrations.wants_matching`（運営あっせん希望か）を持つことで、個人参加（運営振り分け）とチーム応募（自分で組む）を1イベント内に共存させる。

**「参加表明 ≠ 応募完了」**: 参加表明（個人スコア提出等）は `registrations.status='pending'` 等で表し、チーム確定や本応募完了を別段階として扱う。

**self応募の確定・承認フロー（PR-3a/3b で実装）**:
1. 応募者は応募者一覧・チーム編成画面を閲覧でき、編成を**試算**できる（保存しない）。
2. 組みたいメンバーとの合意は**アプリ外（Discord）**で取る（招待制は採らない・軽さ優先）。
3. 代表1人が試算チームを**「確定」**＝ `teams(status='pending')` ＋ `team_members` を作成（代表＝`captain_registration_id`）。確定できるのは `team_formation='self'` のイベント（self/team/mixed）の approved 応募者。`entry_type`・`wants_matching` では絞らない（あっせん希望者も誘われて self で組めるため）。
4. 主催者が**承認**すると `status='approved'` ＝チーム成立。このとき初めて `events.current_count` を排他カウント（pending は定員枠を確保しない）。却下は `status='rejected'`。
5. 確定後の取り下げは代表本人が pending のときのみ可能。二重所属は `team_members.UNIQUE(registration_id)` が構造的に防ぐ。

### 3.4.2 募集フォームのカスタマイズ（フォームビルダー・確定）
イベント作成者が募集フォームの項目を取捨選択できる。データの"固さ"で持ち方を分ける。

**構造化項目（システムが意味を理解する → 専用カラム＋ON/OFFトグル）**
振り分け・計算・表示にシステムが使うデータ。`events` のフラグで出し入れする。
| 項目 | events のフラグ | 用途 |
|------|------|------|
| 個人スコア（ランク申告） | `require_score` | 振り分け・チーム平均計算。初心者向けは false |
| 希望ロール | `require_role` | 振り分け・ロール別構成 |
| マッチング希望 | `allow_matching_choice` | OSLハイブリッドの分岐（registrations.wants_matching） |
| Battle Tag表示 | `require_battle_tag` | イベントでBattle Tagを使うか（通常は常時利用可） |

→ `require_score=false` ならランク欄を出さず、振り分けは平均なしの手動になる。

**自由項目（ただ集めて表示するだけ → フォームビルダー）**
自己紹介・意気込み等。運営が任意の質問を追加できる。入力型は基本5種（text / textarea / select / url / number）。
- `event_form_fields`: イベントに紐づくカスタム質問定義
- `registration_answers`: 各応募者の回答

> 設計の格言: **「計算に使うデータは構造化して持て。表示するだけのデータは柔軟に持て」**。
> ランク等の構造化データを自由項目に混ぜると、後で平均計算ができない等の事故になるため厳密に分離する。

### 3.4.1 イベント進行形式（OSL実運用ベース・確定）
実運用スプレッドシート（OSL Season2）から確認した進行形式に対応する。

- **予選グループ ＋ 決勝トーナメントの2段階**を主対応とする。
  - 予選: グループ（A〜D等）に分け、グループ内総当たり → 上位を抽出。
  - 決勝: 抽出チームによるトーナメント（シングルエリミネーション＋3位決定戦。**実装: 本戦-5a/5b/5c**）。
    - 進出: 各ブロック上位N（主催者がN設定）をシードに、進出数以上の最小2の累乗ブラケット＋BYE（標準シード）。
    - 結果入力（5b）: スコア＝取マップ数→勝者算出。入力者＝主催者＋対戦両チーム代表（予選と共通）。
    - 勝者の**自動進出**: 結果確定で勝者が次ラウンドへ。修正で勝者が変わると下流の対戦配置と結果を**連鎖リセット**（下流に結果がある修正は確認ダイアログ）。
    - トーナメント試合は**奇数BO強制**（引分が出ると進出先が決まらないため）。
    - **3位決定戦（5c）**: イベント設定でON/OFF。準決勝が2試合（4チーム以上）のとき、準決勝の2敗者で3位を決める。決勝と同じ最終roundに配置。
    - **進出チームの手動微調整（5c）**: 1回戦のチームをD&Dで入れ替え（BYE/シードチームも対象）。結果が1件でも入ると入れ替えは不可（全体ロック）。
    - **表彰台（5c）**: 決勝確定で優勝・準優勝、3位決定戦の勝者で3位（3決なしは準決勝敗者2チームを3位タイ）をブラケット上部に表示。
- スプレッドシートから判明した追加要素（要件・設計に反映）:
  - **レギュラー/リザーブ**: チームメンバーに補欠の概念がある（`team_members.position`）。
  - **チーム代表者**: メンバーに代表フラグ（`team_members.is_representative`）。
  - **リプレイコード**: OW独自。試合に観戦/検証用のリプレイコードを紐付ける（`matches.replay_code`）。
  - **提出物ステータス**: アイコン提出等の管理（運営の確認用フラグ）。
  - シート構成（参加チーム一覧 / 予選グループ / スケジュール＆リプレイコード / トーナメント表 / ルール・マップ）は、ほぼそのままテーブル・機能の単位に対応する。

### 3.4.3 スクリム（練習試合）管理（Phase 3 #7・確定）
本戦（イベントの試合）とは別に、**チーム単位の練習試合（スクリム）**をカレンダーで管理する。
- 価値: せっかくカレンダー機能があるので活かす。チームの予定（スクリム・練習）を集約し、**Discord DM通知（3.5.2）で「ほぼ必ず予定に気づける」**ことが本機能の中心価値。
- 本戦の `matches` とは**別概念**（`scrims` テーブル）。スクリムは相手が外部チームのこともあり、勝敗が順位に影響しない。
- 持つ情報（想定）: 対象チーム / 日時 / 相手（自由入力可） / メモ / 配信URL など。
- 通知: スクリム予定が登録/変更されると、対象チームのメンバーへ**個人向け通知（アプリ内＋Discord DM）**。「本日21:00からスクリムです！」のように飛ばす。

### 3.5 通知の2分類（重要な設計区別）
| 種別 | 例 | 実現方式 |
|------|-----|---------|
| (A) ライブ更新 | 結果入力した瞬間、全員の順位表が動く | **Supabase Realtime**（DB変更を検知して全クライアントにpush） |
| (B) スケジュール通知 | 「21時から試合が始まります」 | **Cron（定期実行）** が指定時刻に発火 → Discord webhook投稿 + DBフラグ更新 → Realtimeで開いている人の画面にもバナー表示 |

```
[21時になる] → Cronが発火 → Discord webhookに投稿 + DBにフラグ
                                              ↓
                              Supabase Realtimeが検知
                                              ↓
                        アプリを開いている人の画面にもバナー表示
```

### 3.5.1 シリーズ・開催回・フォローの設計（確定）
**問題意識**: 「イベント」は開催回（OSL Season2 等）であり、継続する主体ではない。第1回をフォローしても第2回告知は届かない。継続して追いたい対象＝**シリーズ**を独立概念として持つ。

**3階層のモデル**
```
event_series（シリーズ）  例: "OSL（社会人OW部リーグ）"
      │ 1対多
      ├─ events: OSL Season1   ← 開催回（実際の応募・試合の単位）
      ├─ events: OSL Season2
      └─ events: OSL Season3
```
- `events.series_id`（任意）。単発イベントは series_id = null でよい。

**フォロー対象は3種（すべて通知対象）**
| フォロー対象 | 通知されるもの |
|------|------|
| シリーズ | 新シーズン（新しい開催回）が告知された |
| 開催回（event） | 応募したイベントの日程確定・結果更新（応募者は自動フォロー想定） |
| 主催者（user） | その人が新しいシリーズ/イベントを立てた |

**シリーズの共同運営（owner/admin の2段階）**
- `series_members`: シリーズに対する運営メンバー。role = `owner`（全権限：運営の追加削除・シリーズ削除）/ `admin`（イベント運営業務）。
- イベント開催中でも運営追加可。
- **招待方法 = 検索招待**: Battle Tag/Discord名でユーザー検索 → 招待 → 相手が承認（`status: invited→active`）。本人同意ありで権限付与を健全化。フォロワー/よく絡む人を候補としてサジェスト表示し選びやすくする。

### 3.5.2 通知の宛先分類と配信チャネル（Discord連携・確定）
**前提**: このアプリは Discord/SNS ほど頻繁に開くものではない。アプリ内通知だけでは見落とす。Discord に通知を流すことで見落としを減らし、コミュニティの盛り上げに貢献する——これが通知設計の中心的な価値。

**通知は「宛先」で2分類する（種別=3.5、宛先=ここ）**
| 宛先分類 | 例 | 配信チャネル |
|------|-----|------|
| **全体向け** | イベント公開告知 / 「本日21時から各試合！」（イベント全体の予定） | アプリ内 ＋ **Discord Webhook（告知チャンネルへ投稿）** |
| **個人向け** | 参加確定 / 「あなたの試合は本日21時」 / スクリム通知 | アプリ内 ＋ **Discord Bot DM（個人へ直接）** |

> 個人向け通知を全員のチャンネルに流すのは不適切（無関係な人へのノイズ＆本人の見落とし）。宛先で配信先を分ける。

**Discord連携の3レイヤー**
| レイヤー | 届く先 | 仕組み | 必要なもの |
|------|------|------|------|
| アプリ内通知 | 各ユーザーの通知一覧 | Supabase Realtime | （既存） |
| Discord Webhook | サーバーの告知チャンネル | Webhook URLにPOST | チャンネルでWebhook発行→登録（Bot不要） |
| Discord Bot DM | フォロワー/参加者個人のDM | Bot がDM送信 | Bot作成・サーバー導入。相手のDM許可が必要 |

**個人向けは「二段構え（アプリ内＋Discord DM）」を正式要件とする**
- 個人通知は **アプリ内に必ず記録**（確実な記録）＋ **Discord DM を送る**（見落とし防止のブースト）。
- 理由: DM単独だと「DM拒否設定の人に届かない＝通知が消える」事故になる。アプリ内に必ず残すことで**誰も取りこぼさない**。DMは"おまけ"ではなく価値の中心だが、確実な土台（アプリ内）の上に乗せる。
- **既存設計がそのまま活きる**: `notification_events`（出来事）→ 宛先集約 → 配信、の配信レイヤーに「Discord DM」を足すだけ。
- **実装順**: アプリ内通知 → その直後に Bot DM 配信を追加（Webhookによる全体告知はPhase1から軽く導入可）。
- **着手方針（分割・確定）**: ①アプリ内通知の土台 → ②フォロー基盤 → ③出来事→通知生成（3.6.1）→ ④Discord Webhook → ⑤Discord Bot DM → ⑥シリーズ概念 → ⑦Cron、の依存順。土台①は「RLSポリシー整備＋`/notifications`一覧＋ヘッダー🔔＋Realtime＋応募確定1種の接続」から。詳細は devlog 2026-07-01「通知機能の着手方針」を参照。

**告知（全体向け）の自動投稿**
- イベント公開・スケジュール確定・試合直前(Cron)・結果確定などを、登録済みWebhook経由で告知チャンネルに自動投稿。
- 主催者がURLを手動コピペする運用も選べる（公開URLは常に発行される）。自動投稿はデフォルトで有効化しつつ手動も可能。

### 3.6 同時申込の排他処理（Phase 3 #6）
- 排他制御の本体は **アプリサーバーではなくDB（PostgreSQL）** が担う。
- **二段構え**:
  - 楽観的ロック（`version`列）: 読んだ時と書く時のversionが一致する時だけ更新。不一致なら弾く。
  - DB制約: `current_count < capacity` をトランザクション/条件付きUPDATEで担保し、アプリのロジックがすり抜けても二重登録を防ぐ。
- アプリ側は親切なエラーを返し、DBで最終防衛する。

### 3.6.1 通知の重複排除（フォロー多重時の事故防止・確定）
複数の対象（シリーズ＋主催者など）をフォローしていると、1つの出来事で複数通知が飛ぶ事故が起きる。これを防ぐ。

**設計原則**: 「誰がフォローしているか」を起点に通知を作らず、「**何が起きたか（出来事）**」を起点にして宛先を集約・重複排除する。
```
[出来事発生] OSL Season3が告知された（notification_events に1件）
      ↓
[宛先集約] シリーズOSLのフォロワー ∪ 主催者Aのフォロワー ∪ …
      ↓
[ユニーク化] ユーザー単位で重複排除
      ↓
[1人1通] notifications に各人1件生成
```
- **DBで最終防衛**: `notifications.source_event_id` ＋ `UNIQUE(user_id, source_event_id)` で、同一出来事から同一ユーザーへの二重生成を物理的に防ぐ（排他処理3.6と同じ思想）。
- 実装はPhase 3。ただし**シリーズ概念はスキーマに先行投入**する（後付けだと既存イベントの紐付け直しが高コストなため）。

### 3.7 通知イベントカタログ（何が起きたら通知が飛ぶか・確定）
「何に対して通知を飛ばすか」を先に固定する。`notification_events.type`（スキーマ上は `text`）に入れる**文字列はこの表が唯一の正**とし、生成側は必ずここから引く。RLS・一覧UI・宛先集約ロジックはすべてこのカタログを前提に設計する。

**`type` 命名規則**: `snake_case`・「**対象名詞_過去分詞**」（出来事＝すでに起きたこと）。例: `registration_approved`。

**宛先の決まり方（重要な区別）**
- **直接関係者**: 宛先がDBの関係から一意に引ける（応募者本人・チームメンバー・招待相手など）。フォロー不要。宛先集約ロジック（3.6.1）は不要で、対象を直接引いて `notifications` を生成するだけ。
- **フォロー集約**: 宛先が「フォロワー集合の和＋重複排除」で決まる（3.6.1）。②フォロー基盤・③宛先集約ロジックが前提。

| # | `type` | 出来事 | 宛先分類（3.5.2） | 起点 | 担当PR |
|---|--------|--------|------------------|------|--------|
| 1 | `registration_approved` | 応募が承認された（参加確定） | 個人 | 直接関係者 | **①A 土台（今回）** |
| 2 | `registration_rejected` | 応募が却下された | 個人 | 直接関係者 | **済（個人通知拡充・2026-07-06）** |
| 3 | `team_approved` | チームが承認された（self確定→成立） | 個人 | 直接関係者 | **済（個人通知拡充・2026-07-06）** |
| 4 | `series_season_announced` | 新しい開催回が公開された（＝新シーズン告知。単発イベント含む） | 個人 | フォロー集約 | ⑥③（シリーズ→集約） |
| 5 | `event_schedule_confirmed` | 日程が確定した | 全体＋個人 | 直接＋フォロー集約 | ②③ |
| 6 | `event_result_updated` | 結果・順位が更新された | 全体＋個人 | 直接＋フォロー集約 | ②③ |
| 7 | `match_starting_soon` | 試合が始まる（開始2時間前リマインド） | 個人 | 直接関係者 | ⑦Cron |
| 8 | `scrim_starting_soon` | スクリムが始まる（開始2時間前リマインド） | 個人 | 直接関係者 | ⑦Cron＋スクリム機能 |
| 9 | `event_matches_today` | 「本日◯時から各試合」（イベント全体の予定） | 全体 | フォロー集約 | ④⑦（Webhook＋Cron） |
| 10 | `scrim_scheduled` | スクリム予定が登録/変更された | 個人 | 直接関係者 | スクリム機能（Phase3 #7） |
| 11 | `series_member_invited` | シリーズ運営に招待された | 個人 | 直接関係者 | ⑥シリーズ |

**旧「#4 イベント公開（`event_published`）」は削除し #4 `series_season_announced` に統合した**（壁打ち確定）。理由: **非公開イベントはフォローできない＝公開の瞬間に event フォロワーはゼロ**なので event フォロワー宛ての「公開通知」は空振り。「新しい開催回が公開された」の宛先は 3.5.1 に従い **series フォロワー ∪ 主催者（user）フォロワー**。単発イベント（`series_id=null`）は主催者フォロワーだけに飛ぶ。1つのDB操作（公開）＝1出来事に統合することで 3.6.1 の二重通知事故も防ぐ。

**リマインド（#7/#8）は「開始2時間前」の相対発火**（壁打ち確定）。試合・スクリムそれぞれの開始時刻の2時間前に飛ばす。**試合とスクリムは type を分ける**（`match_starting_soon` / `scrim_starting_soon`）ことで、文面をサーバー側で出し分ける（「あなたの試合が2時間後に始まります」／「本日のスクリムが2時間後に始まります」）。絶対時刻（毎日◯時にまとめて）ではなく相対にした理由: ユーザー要望が「予定の2時間前」だから。Cron は数分間隔で回し「この後2時間以内に開始し、まだリマインド未送信の試合/スクリム」を拾う（`notification_events` ＋ `UNIQUE` で二重送信を物理防止）。

**土台①Aで接続するのは #1 のみ**（`registration_approved`）。宛先が応募者本人で自明・フォロー不要・既存の応募承認フローに乗せるだけ、が理由。残りは各担当PRの着手時に、この表の `type` と宛先分類を前提に実装する。

**未確定（各担当PR着手時に壁打ちで詰める）**:
- #5/#9 の「日程確定」「本日の試合」の発火粒度（イベント単位か試合単位か）。Cron設計と一緒に決める。
- #4/#5/#6 の全体向け（Webhook）と個人向け（フォロワー）の**二重生成の扱い**（1出来事から全体1件＋個人N件を作るか、宛先で1レコードに集約するか）。③宛先集約の実装時に確定。

## 4. 技術スタック

| レイヤー | 技術 | 理由 |
|---------|------|------|
| フレームワーク | **Next.js (App Router) + TypeScript** | Web開発経験あり。フロント/API一体。型が一気通貫 |
| UI | **Tailwind CSS + shadcn/ui** | 高速に綺麗なUIを構築 |
| DB / 認証 / Realtime | **Supabase (PostgreSQL)** | DB・Discord OAuth・Realtimeが一体 |
| ホスティング | **Vercel** | Next.jsと相性最高・無料枠 |
| 定期実行 | **Vercel Cron** または **pg_cron** | スケジュール通知用 |
| 通知 | **Discord Webhook / Bot** | コミュニティ連携 |
| トーナメント表 | 専用ライブラリ（⑤実装時に選定） | トーナメント/総当たり表の生成 |
| カレンダー | `react-big-calendar` 等（③実装時に選定） | 参加イベントのカレンダー表示 |

### 4.1 アーキテクチャ選定の根拠（フルスタックを選んだ理由）
バックエンドを分離せず Next.js フルスタックとした判断のトレードオフ。

**フルスタックを選んだ理由**
1. **バックエンドが薄い**: 大半が「DBへのCRUD」「Discord webhook」「振り分け計算」。専用APIサーバーを立てるほどの重さがない。
2. **開発者が1人**: 分離の最大の利点（フロント/バックの独立開発）が1人開発では効かず、リポジトリ・デプロイ・型同期が倍になるコストだけ被る。
3. **型の一気通貫**: 同一TSプロジェクトでDB→API→画面まで型が繋がる。
4. **デプロイ・無料枠の単純さ**: Vercelへの1回のデプロイで完結。

**正直なデメリット（許容する）**
- ベンダーロックイン気味（Server Actions等のVercel/Next.js依存）。
- 重い処理に弱い（サーバーレス関数の実行時間制限）。
- バックエンドの独立スケールができない。

**それでも今回問題にならない理由**
- 想定同時アクセスはコミュニティ内の数十〜数百人規模。
- 重い処理が将来出ても、その部分だけ Supabase Edge Functions / Cron に切り出せる。
- 設計原則: **「分離は必要になってからでも遅くない。早すぎる最適化を避ける」**。

### 4.2 Phase 3 機能のフルスタック実現方式（確認済み）
| # | 機能 | 担当レイヤー・方式 |
|---|------|------|
| 1 | イベント検索 | PostgreSQL全文検索 / `ilike`。件数増は `pg_trgm` で高速化 |
| 2 | フォロー＆通知 | `event_series`/`follows`（series/event/user）＋ 出来事起点の宛先集約・重複排除（3.6.1）＋ Realtime/Cron→Discord |
| 3 | カレンダー表示 | フロント（`react-big-calendar`等）＋ 通常クエリ |
| 4 | ユーザー登録・ログイン | Supabase Auth（Discord OAuth のみ） |
| 5 | カテゴリ・タグ付け | `tags`マスタ ＋ `event_tags` 中間テーブル（多対多） |
| 6 | 同時申込の排他 | 楽観的ロック＋DB制約（3.6参照） |

→ 6機能すべて Next.js Route Handlers / Server Actions ＋ Supabase の範囲内。専用バックエンド不要。
