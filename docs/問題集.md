### Q3. データアクセスの3経路

GameEventBoard には「読み取り（表示）」「変更（フォーム送信・編成確定）」「ライブ更新の購読」という3種類のデータアクセスがあります。**それぞれ何を使い、どの Supabase クライアント（`server.ts` / `client.ts`）を使いますか？**

### Q4. RLS（Row Level Security）とは何か

GameEventBoard は全テーブルで RLS を有効化し、「デフォルト拒否（ポリシー未定義＝不可）」から始めています。**RLS とは何をする仕組みで、アプリ層の認可チェックと何が違いますか？** 「アプリがすり抜けても守る」とはどういう状況を指しますか？

<details>
<summary>ヒント</summary>

RLS は DB の行1つ1つに「誰が読める/書けるか」の条件を付ける仕組み。`auth.uid()` が使えることに注目。Server Action のログイン確認をうっかり書き忘れた／別経路（REST）から叩かれた、という状況を想像してみてください。
</details>

### Q5. JST 入力 → UTC 保存 → JST 表示

GameEventBoard は日時を「JST で入力・UTC(`timestamptz`) で保存・JST で表示」という方針で扱っています。`actions.ts` の `jstLocalToUtcIso()` は `datetime-local` の文字列（例 `2026-07-20T21:00`）に `+09:00` を付けて `Date` に渡しています。**なぜ UTC で保存し、入力・表示は JST に変換するのですか？** タイムゾーンを意識せず「入力された文字列をそのまま保存」すると、どんな不具合が起きますか？

<details>
<summary>ヒント</summary>

「文字列 `2026-07-20T21:00` をそのまま保存」だと、それが何時のことか（どのタイムゾーンの21時か）が失われる。UTC という絶対時刻を1つ持っておけば、表示側で好きなタイムゾーンに変換できる。
</details>

### Q6. Zod によるマスアサインメント対策

イベント作成 Server Action `createEvent` は、`organizer_id` と `status` を **フォーム入力から取らず、サーバー側で固定** しています（`organizer_id: user.id`, `status: "draft"`）。**「マスアサインメント（Mass Assignment）」とは何の脆弱性で、なぜこの2つをフォームから受け取ってはいけないのですか？** Zod スキーマ（`schema.ts`）はこの対策にどう寄与していますか？

<details>
<summary>ヒント</summary>

もし `organizer_id` をフォームから受け取ったら、攻撃者は他人を主催者にした（あるいは他人名義の）イベントを作れてしまう。`status` を受け取ったら審査を飛ばして即公開できてしまうかも。Zod は「定義した項目以外は受理しない」ことで、余計なカラムの混入を構造的に防ぐ。
</details>

### Q7. 操作系 Server Action の「防御の段取り」

`publishEvent` / `updateEvent` / `decideRegistration` などの操作系 Server Action は、共通の「防御の段取り」で始まります。**次の①〜④は、なぜこの順番・この形で書かれているのですか？**

```typescript
// ① ログイン確認
const { data: { user } } = await supabase.auth.getUser();
if (!user) return { error: "ログインが必要です。" };

// ② 対象を取得し所有者確認
const event = await findEventById(eventId);
if (!event || event.organizer_id !== user.id) {
  return { error: "このイベントを公開する権限がありません。" }; // ← ③
}

// ④ 状態遷移の検証
if (!canPublish(event.status)) { return { error: publishRejectionReason(event.status) }; }
```

とくに、**③で「イベントが存在しない場合」と「他人のイベントの場合」を同じエラー文にしている**のはなぜですか？

<details>
<summary>ヒント</summary>

- ①が「最後の砦」と呼ばれる理由（別経路から呼ばれても最初に弾く）。
- ②は IDOR（別のIDを指定して他人のデータを操作する攻撃）対策。`organizer_id !== user.id` の意味。
- ③「存在しない」と「権限なし」を区別すると、攻撃者に何が漏れるか？（存在する ID の列挙）
- これはアプリ層の防御。DB 層の RLS（`events_update_own` / 0004）はどんな役割？
</details>

### Q8. IDOR — 2テーブルを跨ぐ所有権確認

`decideRegistration`（応募の承認/却下）は、`registrations` テーブルの1行を更新しますが、権限があるのは **その応募が属するイベントの主催者** です。コードは `findRegistrationWithEvent` で応募とイベントを一緒に取得し、`event.organizer_id !== user.id` を確認しています。**なぜ「応募ID だけ」では所有権を確認できず、イベントまで辿る必要があるのですか？** これを怠るとどんな攻撃が成立しますか？

<details>
<summary>ヒント</summary>

`registrations` には「主催者は誰か」の情報がない。主催者は `events` 側にいる。「registrationId → その event → organizer_id」と辿って初めて「自分のイベントの応募か」が分かる。辿らずに承認できると、攻撃者は他人のイベントの応募を勝手に承認/却下できてしまう。
</details>

### Q9. 同時申込の排他制御（楽観的ロック＋条件付き UPDATE）

チーム枠（定員）の申込で、`incrementEventCount` は「現在値を読み → `capacity` 未満なら → `version` 一致を条件に +1 更新」します。更新行が0なら満員 or 競合として弾きます。**「単に読んで、if で満員判定して、+1 で書き込む」という素直な実装だと、2人が同時に申し込んだとき何が起きますか（レースコンディション）？** `version`（楽観的ロック）と「条件付き UPDATE」がこれをどう防いでいますか？

```typescript
const { data } = await supabase
  .from("events")
  .update({ current_count: ev.current_count + 1, version: ev.version + 1 })
  .eq("id", params.eventId)
  .eq("version", params.expectedVersion)   // ← ここが肝
  .select("id")
  .maybeSingle();
return data ? { ok: true } : { ok: false };
```

<details>
<summary>ヒント</summary>

- 素直な実装：2人が同時に「残り1枠」を読む → 両方 if を通過 → 両方 +1 → 定員オーバー。
- `version` を条件に入れると、先に成功した方が version を進めるので、後から来た方の UPDATE は「対象行なし（0件）」になる。「読んだ時点から変わっていないこと」を UPDATE 自身に検証させている。
- さらに DB 層の CHECK 制約・UNIQUE 制約が「最終防衛」。アプリのロジックがバグっても DB が守る。
</details>

### Q10. Realtime が配信されない — `realtime.setAuth()`

`NotificationsRealtime` は自分宛て通知の INSERT を Realtime で購読し、来たら `router.refresh()` します。実装では `subscribe()` の前に **`supabase.realtime.setAuth(session.access_token)`** を呼んでいます。**これを書かないと、RLS 配下の `notifications` テーブルの変更が「なぜか届かない」という現象が起きます。理由を説明してください。**

<details>
<summary>ヒント</summary>

`postgres_changes` は RLS を尊重する。RLS は「その行を読める人か？」を評価するが、Realtime 側に購読者の JWT（アクセストークン）を渡していないと「未認証」として RLS に弾かれ、変更が配信されない。`setAuth()` で購読者のトークンを Realtime に教えている。
</details>

### Q11. 通知の重複排除 — 出来事起点 ＋ `UNIQUE(user_id, source_event_id)`

通知は「出来事（notification_events）を1件記録 → 宛先を集約・ユニーク化 → 1人1件の notifications を作る」という流れで、`notifications` には `UNIQUE(user_id, source_event_id)` が張られています。さらに宛先の生成は `Promise.allSettled` で並列に行い、失敗は握ってログのみ（ベストエフォート）です。**同じ出来事から同じ人に通知が2回作られそうになったとき、二重通知を防いでいるのは何ですか？** また、「フォロワー1000人のうち1人への通知生成が失敗しても、残り999人には届く」ようにするために `allSettled` を使う理由は？

<details>
<summary>ヒント</summary>

- 宛先集約（`aggregateRecipients`）で和集合＋重複排除するのがアプリ層の対策。だが集約漏れや二重発火に備えて `UNIQUE(user_id, source_event_id)` が **DB 層の最終防衛**（物理的に2行目を拒否＝冪等）。
- `Promise.all` は1件でも reject すると全体が失敗扱いになる。`allSettled` は各宛先を独立に扱うので、1件の失敗が他を巻き込まない（部分配信を防ぐ）。
</details>

### Q12. スコア算出 — 未認定セルの補完3方式

スコアあり応募では「ロール × シーズン」の2次元グリッドを平均して個人スコアを出しますが、OW はロール毎に認定が要るため「未認定セル」が生じます。`scoring.ts` は主催者が選んだ方式で未認定を埋めます：**`fill_by_role`（横軸補完）/ `fill_by_season`（縦軸補完）/ `exclude`（除外）はそれぞれどう埋めますか？** また「縦軸補完だが同ロールが全シーズン未認定」「全グリッドが未認定」といった端ケースは、それぞれどう扱う仕様ですか？

<details>
<summary>ヒント</summary>

- `fill_by_role` … 同一シーズンの他ロール平均で埋める。その列が全ロール未認定なら列を除外。
- `fill_by_season` … 同一ロールの他シーズン平均で埋める。その行が全シーズン未認定なら行を除外。
- `exclude` … 未認定セルは平均に含めない。
- 除外した結果、有効な値が1つも無ければ `base = null`（スコアなし）。`scoring.ts` の `calcGrid` / `calcSingleRole` の実装と、[スコアリング設計](./スコアリング設計.md) の「端ケースの確定仕様」を照合してみてください。
</details>

### Q13. security definer 関数の認可バイパス（0037 の監査）

マイグレーション 0037 では、`create_series_with_owner` の引数から `p_created_by` を廃止し、関数内で `auth.uid()` を使うよう変更しました。また `upsert_notification_event` の `EXECUTE` 権限を `anon` / `authenticated` から `REVOKE` しました。**もとの `create_series_with_owner(..., p_created_by uuid)` には、どんな権限昇格の穴があったのですか？** Postgres の security definer 関数と「`EXECUTE` がデフォルトで `PUBLIC` に付与される」性質が、この穴とどう関係しますか？

<details>
<summary>ヒント</summary>

- `p_created_by` を引数で受けると、REST の `/rpc/create_series_with_owner` を直接叩いて **他人の UUID を渡し、他人名義（owner）のシリーズを勝手に作れた**。actor は「引数」ではなく「セッション（`auth.uid()`）」から取るべき。
- security definer は「関数の所有者権限」で実行される（RLS を越えられる）。しかも `EXECUTE` がデフォルトで PUBLIC。だから内部で認可（`auth.uid()` チェック）を持たない definer 関数は、誰でも叩ける穴になる。
- 「Server Action 経由だと安全に見えても、RPC/REST 直叩きで穴が露見する」という教訓（[devlog](./devlog.md) のロジック層セキュリティ監査）。
</details>

### Q14. なぜ Prisma を入れず、Supabase クライアント（クエリビルダー）＋型自動生成にしたのか

採用担当者に「Node なら Prisma が定番では？なぜ入れなかったのですか？」と聞かれました。どう答えますか。**RLS との相性・Auth/Realtime との連携・マイグレーションの二重管理・型安全** の4観点で、Prisma を足すデメリットと、`supabase gen types` で何を代替したかを説明してください。

<details>
<summary>ヒント</summary>

- Prisma は直接 DB に繋ぎユーザーセッションを通さない → RLS をすり抜けやすい。本設計は RLS を最終防衛の柱にしているので相性が悪い。
- Supabase クライアントはユーザーのセッションを引き継ぎ RLS 配下で動く。Auth/Realtime とも自然に繋がる。
- マイグレーションは `supabase/migrations/*.sql` 一本。Prisma schema と二重管理しない。
- Prisma の主目的（型安全）は `gen types typescript` でほぼ同等を確保。→「Supabase を"ただのDB"として使うなら Prisma も有効。だが本プロジェクトは Supabase の機能を活用するので不採用」という結論の型。[アーキテクチャ設計書 3.3](./アーキテクチャ設計書.md)。
</details>

### Q15. なぜ認可を「アプリ層 ＋ DB層（RLS）」の2層にするのか

「Server Action で `organizer_id !== user.id` を確認しているなら、RLS は要らないのでは？（二度手間では？）」と聞かれました。**あえて2層にする理由**を、それぞれの層が何を担当するか（親切なUI/エラー vs 最終防衛）を軸に説明してください。逆に「RLS だけにしてアプリ層チェックを省く」ではダメな理由も答えてください。

<details>
<summary>ヒント</summary>

- アプリ層 … 画面・操作の出し分け、親切なエラー文（「権限がありません」）。ユーザー体験を作る。
- DB層（RLS） … 最終防衛。アプリのバグ・別経路（REST直叩き）でも守る。
- 「RLS だけ」だと、弾かれたとき生の DB エラー（42501 等）しか返せず UX が悪い。ボタンの出し分けもできない。
- 「アプリ層だけ」だと、1箇所書き忘れ／別経路で即穴。排他制御・通知重複排除と同じ「DB で最終防衛」思想。[アーキテクチャ設計書 4.2](./アーキテクチャ設計書.md)。
</details>

### Q16. 認可の「置き場所」— 操作系と閲覧系で非対称なのはなぜか

GameEventBoard では、**操作系（作成・更新・削除）は Server Action の `if` チェックが主役**で、**閲覧系（一覧・詳細の公開）は RLS が主役**です。同じ「認可」なのに、力点を置く場所が操作系と閲覧系で非対称なのはなぜですか。

<details>
<summary>ヒント</summary>

- 操作系は「親切なエラー・状態遷移の検証・楽観ロック」など、アプリ層でしか書けない判断が多い。RLS は最終防衛として後ろに控える。
- 閲覧系は「published は全員・下書きは主催者だけ」のような単純な出し分けが多く、RLS のポリシー（`events_select_visibility` / 0005 等）で宣言的に書ける。SELECT のたびに `if` を書くより DB で一括で効かせた方が漏れない。
- 「どちらの層も使うが、主役が違う」という理解が要点。
</details>

### Q17. なぜランクを「プロフィールに常設せず、応募のたびに入力」するのか

初期設計では「ランクをプロフィールに事前登録（`user_season_ranks` に永続）」する予定でしたが、実運用に合わせて **「応募時に入力・非永続」** に変更しました（`user_season_ranks` / `user_peak_achievement` は当面使わない）。**この変更の理由と、常設プロフィール方式のどんな事故を避けたのか**を説明してください。トレードオフ（毎回入力の手間）はどう緩和していますか？

<details>
<summary>ヒント</summary>

- OW のランクは毎日変動しうる。常設だと「古いランクのまま応募する事故」が起きる。前回値を初期表示するのも同じ罠。
- 何シーズン参照するかは主催者がイベントで決める（`events.declared_seasons`）ので、そもそも人に固定できない。
- 手間の緩和：バトルタグは `users.battle_tag` に保存して次回応募で自動補完（ランクとは別扱い）。[スコアリング設計 1章](./スコアリング設計.md)。
</details>

### Q18. なぜチームスコアを保存せず、常に算出するのか

`team-score.ts` の `teamScore()` は「出場（regular）メンバーの実効スコア平均」を毎回計算し、DB に保存しません（実効スコア ＝ `organizer_override_score ?? final_score`）。**チームスコアをカラムに保存しない設計判断の理由**を、「交代シミュレーション」というこのアプリの中核価値と絡めて説明してください。保存する場合のデメリット（整合性）は何ですか？

<details>
<summary>ヒント</summary>

- 編成中はメンバーが D&D で頻繁に動き、リザーブとの交代を「総当たりで試算」する。保存値だと1手ごとに再計算・再保存が要り、ズレの温床になる。
- メンバー構成（team_members）が真値で、チームスコアはそこから **導出される値**。導出値を二重に持つと整合性を保つ責任が増える。
- `swapCandidates()` は仮編成を作って `teamScore()` を呼ぶだけ、という純粋関数で済む（DB非依存でテストできる）。[DB設計書 4.2/4.3](./DB設計書.md)。
</details>

### Q19. なぜ Discord Bot を「常駐させず」REST を都度叩くのか

通知の外部配信で、全体告知は Webhook、個人向けは Bot の DM を使います。Bot は **常駐（ゲートウェイ接続）せず、Vercel の関数（Cron / Server Action）から Discord REST API を都度叩く** 方式にしました（2026-07-07 確定）。**なぜ常駐 Bot にしなかったのですか？** どういう機能が必要になったら常駐を検討しますか？ また、この判断は「Vercel サーバーレス」という土台とどう噛み合っていますか？

<details>
<summary>ヒント</summary>

- 今回の Bot は「送信専用」。DM 受信・スラッシュコマンド応答はしない。送信だけなら常駐ゲートウェイ接続は不要で、REST を都度叩けば足りる。
- 常駐プロセスは Vercel サーバーレス（短命な関数）と噛み合わない（常時起動を別で用意する必要が出る）。「送信にはトークンが要るが常駐は要らない」という切り分け。
- 将来ユーザー↔Bot の対話機能をやるなら初めて別プロセス常駐を検討。[アーキテクチャ設計書 5章](./アーキテクチャ設計書.md)。
</details>

### Q20. スコアなし応募のもう1パターン（「ランク収集する＋算出しない」）

壁打ちで、オーナーの運用には「ランク収集」と「スコア算出」が **独立した2軸** だと分かりました。現状は ①収集＋算出（`require_score=true`）と ③収集しない＋算出しない（`require_score=false`）は表現できますが、**②「ランクは集めるが、スコアは算出しない（実力均等化のため運営が目視で見る初心者向け）」だけ表現手段がありません**。この②を実装するとしたら、どこを変更しますか？設計方針を考えてください。

### Q21. 交代シミュレーションに「ロール構成の維持」を足す

現状の `swapCandidates()` は「全レギュラー総当たり」で交代候補を出しますが、OW は タンク1・DPS2・サポート2 のロール構成を保つ必要があります。**「同ロール同士の交代だけ」に絞る**としたら、`MemberScore` に何を足し、`swapCandidates` のロジックをどう変えますか？ 「総当たり」と「同ロール限定」を主催者が切り替えられるようにする場合の設計は？

<details>
<summary>ヒント</summary>

- `MemberScore` に `role`（tank/dps/support）を持たせ、`out.role === reserve.role` の組だけ候補にする。
- 純粋関数のまま拡張できる（DB非依存の利点）。テストは「同ロールのみ候補に出るか」を追加。
- 切り替えフラグは `swapCandidates` の引数 or イベント設定。`team-score.ts` のコメントにある「同ロール限定に絞るか否かは PR-2 で要確認」という宿題そのもの。
</details>

### Q22. 通知の「試合直前リマインド」を Vercel Cron で作る

「21時から試合」の30分前などに、参加者へリマインド通知を飛ばしたいとします。これはユーザー操作起点ではなく **スケジュール起点** なので、Vercel Cron が関数を叩いて出来事を生成します。**どんなジョブ設計にしますか？** とくに「Cron は数分おきに走る」前提で、**同じ試合のリマインドを二重に飛ばさない（冪等にする）** にはどうしますか？

<details>
<summary>ヒント</summary>

- Cron が定期起動 → 「開始 N 分後〜N+α 分の範囲に開始する試合」を拾う → 出来事生成 → 既存の通知フロー（宛先集約 → 1人1件）。
- 冪等性：`notification_events` の `dedup_key`（0031）や `notifications` の `UNIQUE(user_id, source_event_id)` を使い、同じ試合×同じ人に2回作らない。Cron が重複起動しても DB が弾く。
- 「送信済みフラグを試合側に持つ」案との比較も考えてみてください。[アーキテクチャ設計書 2.4/5章](./アーキテクチャ設計書.md)。
</details>

### Q23. ユーザーが100倍に増えたら何が問題になるか

GameEventBoard は Vercel（サーバーレス）＋ Supabase（マネージド）で動いています。OW2 コミュニティで人気が出て、同時に多数のイベント・応募・Realtime 購読が走るようになったとします。**どこがボトルネックになり、どう対処しますか？** 「重い計算は Supabase Edge Functions に切り出す」という設計上の逃げ道（早すぎる分離を避ける方針）とどう繋がりますか？

<details>
<summary>ヒント</summary>

- サーバーレスは水平スケールしやすい（関数は勝手に並列化）。むしろボトルネックは DB（Supabase の接続数・クエリ負荷）や Realtime の同時接続数になりがち。
- 重い算出（大規模イベントのスコア一括計算・振り分け）を Server Action で同期処理し続けると関数のタイムアウトに当たる → Edge Functions / 非同期ジョブへ切り出す。
- 「重い処理が出たら切り出す（早すぎる分離を避ける）」＝いま全部を分散設計にしないのは、バックエンドが薄く1人開発だから。負荷が実際に出てから分離する、という判断の一貫性。[アーキテクチャ設計書 1.3/5章](./アーキテクチャ設計書.md)。
</details>
