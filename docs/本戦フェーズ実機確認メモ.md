## 実機確認シナリオ（通しで1回）

### 前提データ
- **order: チーム編成 → ブロック分け → 対戦 → 結果 → 順位**。承認済み（approved）チームが複数必要。
- 確認には別アカウント（応募者）での self 応募・承認まで必要（RLS が効くため）。
- ダミーデータ投入は `supabase/dev_seed_*.sql`（.gitignore 済み）を利用。

### 手順
1. **イベント作成**（主催者）
   - `team_formation='self'`（応募者がチームを組む）。※フォームに進行形式の入力はまだ無いので DB 直編集が要るかも（要確認・後述の既知の注意点）。
   - 「本戦設定」で**予選BO=3**。
   - 「順位設定」で**順位を集計する=ON**、勝点（例 勝3/分1/負0）、タイブレークを「使う」エリアに D&D で並べる（例: 直接対決→得失マップ差→POTG）。
2. **self 応募 → 承認**（別アカウントで応募 → 主催者で承認）。approved チームを **3〜4チーム**作る。
3. **ブロック分け** `/events/[id]/groups`
   - ブロックを作成（例 Aブロック）。承認済みチームを D&D で振り分け。
   - 別ブロックへ移動で元から消えるか、ブロック削除で中身がプールに戻るか。
4. **対戦表生成** `/events/[id]/matches`
   - 「対戦表を生成」→ 総当たり（4チームなら6試合）が出るか。
   - 各カードに **BO3 バッジ**が出るか。
5. **結果入力**
   - スコア入力欄の**上限が BO に連動**（BO3 なら最大3）しているか。
   - タイブレークに potg を入れたイベントで **POTG 欄が出る**か（入れてないイベントでは出ないか）。
   - 勝者が強調表示・引分表示。修正・取り消しができるか。
   - **対戦両チームの代表（captain）でログインして、自チームが絡む試合だけ入力できる**か（他チーム同士は不可）。
6. **順位表**
   - 結果を入れると順位表が動くか。勝点・得失・(POTG)が正しいか。
   - **タイブレークが効く**か（勝点同着のとき、設定した優先順で順位が決まるか）。
   - 3チーム以上同着で**同着ミニリーグ**の挙動。完全同着は**同順位表示（1,1,3）**になるか。
   - `ranking_enabled=false` のイベントでは順位表が出ないか。

### 特に注意して見るポイント（今日の実装の要）
- **認可の出し分け**: 参加者（応募者）は閲覧のみ、主催者は全操作、代表は自チーム試合の結果入力のみ。アカウントを変えて確認。
- **BO連動**: スコア上限が BO で変わる。再生成しても結果ありの試合は残る（結果保護）。
- **POTG の出し分け**: tiebreakers に potg がある時だけ入力欄。
- **同着の数え方**: ミニリーグ・引分→次基準・全タイブレーク使い切ったら同順位。

## 既知の注意点・未確認事項

- **進行形式（entry_type/team_formation）のフォーム入力は未実装**。イベント作成フォームには「予選BO・順位設定」はあるが、`team_formation='self'` 等は DB デフォルトのまま。self 応募を確認するには **SQL Editor で `update events set team_formation='self' where id=...`** が必要な可能性が高い（PR-3b self 応募の実機確認時と同じ）。
- BO の**スコア上限連動は緩め**（各チーム ≤ best_of のみ。「合計 ≤ best_of」「勝者は過半数」までは強制していない）。2-2 のような BO3 ではあり得ない入力も通る点は仕様（主催者の良識に任せる）。
- group_best_of を**後から変えても既存試合の best_of は変わらない**（再生成で反映＝仕様）。
- 確認用テストイベント UUID（過去メモより）: `fc8a8b72-dbd1-43bf-b860-fed82df94b5c`（role_swap不可・require_score=true・ダミー応募者投入済みのはず）。本戦確認用に順位設定・BO を設定して使うとよい。
