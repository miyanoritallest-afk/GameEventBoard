## 1. セキュリティ（全機能で必須）

Web アプリの主要脅威に対し、以下を**例外なく**適用する。各対策は設計書 4.2「2層で守る（アプリ層＋DB層 RLS）」の思想に基づく。

| # | 脅威 | 対策 | 補足 |
|---|------|------|------|
| 1 | **SQLインジェクション** | Supabase クエリビルダ（`.from().insert()` 等）**のみ**を使う。生SQL文字列の組み立て・連結は**禁止** | `.rpc()` で生SQLを呼ぶ場合は必ずパラメータ化する |
| 2 | **IDOR**（他人のデータをID指定で操作） | アプリ層で所有者チェック ＋ **DB層 RLS で最終防衛**。アプリ層だけに頼らない | RLS ポリシー本体は 0002 マイグレーションで定義 |
| 3 | **XSS** | React の自動エスケープに任せる（`{value}` で表示）。`dangerouslySetInnerHTML` は**原則禁止** | 使う場合は DOMPurify 等でサニタイズ必須 |
| 4 | **認証バイパス** | 操作系（変更）の Server Action は**冒頭で必ずログイン確認**し、未ログインを弾く | 閲覧系は公開、操作系は保護（下記 3章） |
| 5 | **マスアサインメント** | Zod スキーマで**許可カラムのみ**受理する。`organizer_id` / `status` など権限・状態に関わる値は**入力から取らず、サーバー側で固定**する | ユーザー入力を丸ごと insert/update しない |
| 6 | **CSRF** | Next.js の Server Action 標準対策に乗る（追加実装不要） | Route Handler を使う場合は別途検討 |
| 7 | **秘密情報の漏洩** | `SUPABASE_SERVICE_ROLE_KEY` 等のサーバー専用鍵を**絶対にクライアントへ出さない**（設計書 4.5） | Service Role は RLS を無視するため管理用途に限定 |

## 2. 入力検証（バリデーション）

- **専用の guard 層は作らない。** 検証は Controller（Server Action）の責務（設計書 3.5）。層は増やさない。
- 検証ルールは **Zod スキーマ**として機能ごとに外出しし（例: `app/<機能>/schema.ts`）、Controller から呼ぶ。フォームとサーバーで共用する。
- **想定内の失敗**（バリデーションNG・締切超過・定員オーバー等）は**例外を throw せず、戻り値で返す**（例: `{ ok: false, error: "..." }`）。
- **想定外の例外**（DB接続断・バグ）は throw し、Next.js の `app/**/error.tsx`（エラーバウンダリ）が受け止める。**例外処理専用の層は作らない**。
- 文字数・数値範囲の上限を必ず設定し、過大入力を防ぐ。

## 3. 認可（ページ／操作の保護）

「**閲覧系は公開・操作系は保護**」を基本とする。

| 種別 | 例 | 扱い |
|------|----|------|
| 閲覧系 | トップ・イベント一覧・イベント詳細 | 公開（未ログインでも閲覧可） |
| 操作系 | イベント作成・応募・マイページ | 保護（ログイン必須） |

保護ページは**2段で守る**：
- **A（推奨）**: ページ表示前に未ログインを検知し `/login` へリダイレクト。`?redirect=` で元ページへ復帰させると親切。
- **B（必須）**: Server Action 冒頭でログイン確認。直接POSTされても弾く最後の砦。

## 4. データアクセス・層構造

設計書 3.3 / 3.5 に従う。本書では実装時の規律として再掲する。

```
[Controller] app/<機能>/actions.ts   入力検証(Zod) → Service/Repository を呼ぶ（薄い）
      ↓
[Service]    lib/services/           純粋ロジック（計算・判断）。DBに依存しない。単体テストの主役
      ↓
[Repository] lib/repositories/       Supabase クライアント経由の DB アクセスを集約
```

- **複雑ロジック**（スコア算出・振り分け等）は Service に切り出し、テスタブルにする。
- **単純CRUD・表示のみ**は過剰に層分けしない（Server Component から直接クエリ可）。
- 「後でテストする前提」で、計算を Server Action にベタ書きせず Service に寄せる。

## 5. 日時の扱い

- **入力＝JST想定 → 保存＝UTC（`timestamptz`） → 表示＝JST**。
- Next.js / Supabase の標準に乗る。アプリ上の表示は常に日本時間。
